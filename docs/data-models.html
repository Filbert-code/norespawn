NoRespawn — Data Model Design

A foundation-first design for the data that powers the app: the exercise catalog, reusable workout plans, and the live sessions you actually perform — built to be analyzed, extended, and fed to an LLM.

Postgres (Supabase) Relational + normalized Snapshot history Event log Multi-user ready LLM-friendly

1 Overview & the 3 layers

Everything in NoRespawn falls into one of three layers. Keeping them separate is the single most important design decision — it's what lets the app stay clean as features pile on.

① Catalog layer — "what exists"

The reusable library of exercises and their sensible defaults. Global, slow-changing, de-duplicated. This is the menu you build workouts from — now a small knowledge graph (relationships) fed by an AI generation pipeline.

exercise · exercise_relationship · exercise_candidate

② Plan layer — "what I intend to do"

Reusable workout plans produced by the Workout Builder ("Push Day A"). References catalog exercises but can override any default (sets, reps, weight, rest). The Tracker schedules these.

workout · workout_exercise · workout_set

③ Log layer — "what actually happened"

A performed instance on a real date/time: the Live Workout Game. Records actual reps/weight/rest per set, what you skipped, and a timeline of every change you made (fuel for Bob's suggestions).

workout_session · session_exercise · session_set · session_event
Why three layers instead of one? A single "Workout" object that mixes the plan with what happened forces painful choices later: editing an exercise's defaults would rewrite history, you couldn't reuse a plan without copy-pasting, and analytics ("planned vs. actual") become impossible. Splitting them keeps each concern independent and queryable.
How the layers connect, briefly: A workout (plan) is a list of exercises (catalog) with optional overrides. When you press Start Workout, the app snapshots that plan into a workout_session (log) so later edits to the plan or catalog never alter your history. Per-user feelings about an exercise (preference & intensity) live in their own time-stamped table so we can watch them drift over time.

The rest of this doc defines each table field-by-field, with the reasoning behind the choices and notes on what we deliberately left out for later.

2 Conventions & ground rules

A handful of decisions applied consistently across every table. Locking these down now is what makes the schema feel coherent.

Identifiers

Kind of rowID strategyWhy
Catalog rows (exercise) Human-readable slug — text primary key, e.g. "shoulder_press" Stable, readable in URLs/queries/LLM tool calls, and naturally aids de-duplication.
Enumeration lookups (body groups, equipment…) Slug — text primary key, e.g. "shoulders" Same reasons; also lets us attach labels/metadata to each value.
User-owned records (workouts, sessions, sets, events, prefs) UUID — uuid default gen_random_uuid() Non-guessable, collision-free, safe to generate client-side, no enumeration leaks.

Ownership & multi-user readiness

Even though you're the only user today, every user-owned table carries a user_id uuid referencing auth.users(id) (Supabase's built-in auth table). This is free to add now and means multi-user becomes a non-event later — no migration, just turn on the policies.

The catalog is shared, feelings are personal. The exercise catalog has no user_id — it's a global library. Anything subjective or personal (preference, intensity, plans, sessions) is scoped to a user.

Row Level Security (RLS)

Every user-owned table gets an RLS policy of the shape user_id = auth.uid() for select/insert/update/delete. The catalog and enum tables are world-readable (to signed-in users) but writable only via admin/seed jobs. The client-side email allowlist we already built is just a UI gate — RLS is the real enforcement.

Timestamps

Every table carries, at minimum:

  • created_at timestamptz not null default now()
  • updated_at timestamptz not null default now() (bumped by a trigger on update)

All datetimes are timestamptz (UTC under the hood, e.g. your 2026-06-07T14:27:30Z). Never naive timestamps — the calendar/Tracker depends on correct timezone math.

Units

Weight is always pounds (lbs), stored as numeric (not float — avoids 2.5 + 2.5 = 5.0000001 rounding). Durations are stored as integer seconds (rest_seconds, duration_seconds) — trivial to format and to do math on. Distances (for future cardio) would be numeric meters. We standardize on one canonical unit per dimension and format in the UI.

The snapshot principle SNAP

This is the backbone of history integrity. When a value is copied from a higher layer into a lower one at a meaningful moment, we freeze a copy rather than relying on a live reference:

  • Building a plan snapshots the exercise's defaults as the plan's starting numbers (then you can override).
  • Starting a session snapshots the plan into the session's planned columns.
  • Fields that are snapshots are marked with the SNAP tag throughout this doc.
Why snapshot instead of just joining back to the catalog? Because defaults, preferences, and even an exercise's name change over time. If June's session merely pointed at the live catalog, editing "shoulder press" in December would silently rewrite what June says you did. Snapshots make every session an honest historical record, while the exercise_slug reference is kept alongside for grouping/analytics ("show all shoulder-press sessions").

Soft deletes

Catalog exercises use is_archived boolean rather than hard deletes, so historical sessions that reference a retired exercise never break. User data can be hard-deleted (cascades) or archived per table as noted.

3 Enumerations & taxonomy

Constrained value sets. Two flavors, chosen deliberately per case.

Lookup tables vs. fixed enums

ApproachUse forTrade-off
Lookup table (a real table with slug PK + label + metadata) Taxonomy that grows or carries extra data: body_group, body_sub_group, equipment Add values with a plain INSERT (great for AI-generated exercises); can attach labels, icons, sort order, relationships. No migration to add a value.
Postgres enum type (or a CHECK constraint) Small, fixed, code-coupled sets: tracking_type, session_status, set_status, event_type DB-enforced and self-documenting; adding a value needs a tiny migration — which is appropriate because the app's code must handle it anyway.
Rule of thumb: if a value's existence requires new UI/logic, it's a fixed enum. If it's just more data of the same shape (another muscle group, another piece of equipment), it's a lookup table.

4 Exercise (catalog)

The global, de-duplicated library of movements and their sensible defaults. This is the menu the Workout Builder draws from. It holds no user-specific feelings — preference and intensity now live in their own per-user table (next section).

Defaults: flat columns, not a JSON blob

Your sketch nested defaults under a "defaults": {…} object. In Postgres we flatten those into real typed columns (default_sets, default_reps, …).

Why flatten? Your stated goal is "all workout data easy to analyze and structured into tables." Real columns get types, defaults, check constraints, and indexes — you can write AVG(default_reps) or filter WHERE default_weight > 50 trivially. A JSONB blob hides structure, can't be constrained, and is clumsy for the LLM tools you want ("get chest exercises sorted by…"). We reserve JSONB only for genuinely free-form data.

De-duplication mechanism

  1. On insert, compute name_normalized from name (lowercase → trim → collapse spaces → strip punctuation). A DB trigger or generated column keeps it authoritative.
  2. A UNIQUE index on name_normalized makes a duplicate insert fail at the database level — the ultimate guard, even if app logic misses it.
  3. For AI generation later, the tool does a normalized lookup first and either returns the existing slug or inserts a new one (an idempotent "find-or-create").
Variations are distinct rows, disambiguated by name. "Dumbbell Shoulder Press" and "Barbell Shoulder Press" normalize differently, so they coexist. Exact-name de-dup is the floor; semantic de-dup (catching near-duplicates an LLM would invent, like "Seated DB Press") is handled by the embedding-based pipeline in §6.

5 Exercise relationships (the graph)

A tiny self-referencing table that turns a flat catalog into a knowledge graph. One small table powers substitutions, progressions, and auto-supersets — and gives the LLM real edges to traverse instead of guessing from names.

exercise_relationshipcatalog · directed edges
ColumnTypeNotes
from_slugFK → exercisetextSource exercise.
to_slugFK → exercisetextTarget exercise.
typeENUMrelationship_typeprogression / regression / substitute / variation_of / antagonist.
notetext nullOptional ("requires a band").
Composite PK = (from_slug, to_slug, type); CHECK (from_slug <> to_slug).

What it unlocks

  • Equipment swaps — "no barbell today" → follow substitute edges.
  • Make it harder/easier — follow progression / regression for the live "level up" button.
  • Auto-supersets — pair antagonists (biceps ↔ triceps) when building or mid-workout.
  • Canonical rollups — variation_of edges let analytics group all "shoulder press" variants and answer "most re-occurring movement" by family.
  • Smarter LLM — the model traverses explicit edges rather than inferring relationships from text.
Why one generic edge table instead of columns like harder_variant_slug? Relationships are many-to-many and open-ended (an exercise can have several substitutes and progressions). A generic edge table scales to any number of links and new relationship kinds without schema changes — and it's the classic, query-friendly way to model a graph in Postgres.
Direction & inverses. progression and regression are inverses, so we store one direction and infer the other in queries (or a view exposes both). substitute and antagonist are effectively symmetric — the AI pipeline inserts both directions to keep lookups simple.

Sketch SQL

create table exercise_relationship (
  from_slug text not null references exercise(slug) on delete cascade,
  to_slug   text not null references exercise(slug) on delete cascade,
  type      relationship_type not null,
  note      text,
  primary key (from_slug, to_slug, type),
  check (from_slug <> to_slug)
);
create index on exercise_relationship (to_slug, type);

6 AI generation & de-duplication

Since the catalog is strictly AI-generated for now, the pipeline that feeds it is part of the data model. Goal: a pristine, de-duplicated catalog even though an LLM (which loves inventing near-duplicates) is the only author.

Two layers of de-duplication

  1. Exact — the name_normalized unique index (§4). Floor-level guard.
  2. Semantic — an embedding vector (pgvector) on each exercise. Before inserting a candidate, compute its embedding and check cosine similarity against the catalog; if it's within a threshold of an existing row, treat it as a duplicate (or a variation_of edge) instead of a new exercise. This catches "Seated DB Press" vs. "Dumbbell Shoulder Press (Seated)" that normalized names miss.

Staging table: exercise_candidate

AI output lands here first and is promoted to exercise only after dedup + (optional) review. This keeps junk and dupes out of the live catalog the app reads from.

The pipeline

  1. Generate → LLM proposes an exercise; insert into exercise_candidate (pending).
  2. Embed → compute the embedding from name + description.
  3. De-dup check → exact (normalized) then semantic (cosine ≥ threshold). On match → rejected_duplicate with matched_exercise_slug (optionally add a variation_of edge).
  4. Validate → enums/required fields sane? If not → rejected_invalid.
  5. Promote → insert into exercise (source='ai', is_verified=false); mark candidate promoted.
You get a hand-edit UI "for free" later. The same promote/verify machinery is exactly what a future manual-editing UI plugs into — flip is_verified, edit fields, or author rows with source='user'. No schema change needed.
pgvector indexing. Add an HNSW (or IVFFlat) index on embedding for fast similarity search as the catalog grows. Threshold is configurable and the stored similarity lets you tune it from real data.

7 User exercise preferences (over time)

Preference and intensity are personal and they drift — an exercise you loved at score 8 might slip to 4 as it gets stale; intensity changes as you get stronger. So they live here, scoped to a user and time-stamped, not on the global exercise.

Design: append-only history, latest row wins

Rather than overwriting a single "current" value, every change inserts a new row with an effective_at timestamp. The current feeling is simply the most recent row for that (user, exercise) pair. You get a full timeline for free — perfect for the LLM ("preference for incline press has dropped three months running") and for charts.

Why append-only instead of a row you keep updating? An updated row forgets the past. The whole point of pulling these out of exercise was to watch them change. An immutable log is the simplest structure that never loses history and is trivial to query. It's also a natural fit for changes made mid-workout (we can stamp which session caused the change).

Reading the current value

A small view exposes "current scores" so the app and LLM tools don't repeat the query:

create view current_exercise_score as
select distinct on (user_id, exercise_slug)
       user_id, exercise_slug, preference_score, intensity_score, effective_at
from   user_exercise_score
order  by user_id, exercise_slug, effective_at desc;

This directly powers your planned LLM tools — e.g. "get chest exercises sorted by user preference" becomes a join of exercise ↔ current_exercise_score filtered by body group, ordered by preference_score desc.

Seeding the first value — decided. A brand-new user has no score rows yet, and per your call we show "unranked": "no row" simply means no opinion, and the UI presents an unranked state rather than inventing a number. No baseline_intensity on exercise (see Resolved decisions).

8 Workout plan

A reusable plan — the output of the Workout Builder ("Push Day A"). It's an ordered list of catalog exercises, each with its own planned numbers that start from the exercise's defaults but can be overridden freely.

Three tables, increasing granularity

  • workout_exercise — one row per exercise in the plan, in order, with the planned numbers.
  • workout_set — optional per-set overrides, only when sets should differ (pyramids, warmups).

9 Session (live workout)

What actually happened on a real date/time — the Live Workout Game. When you press Start Workout, the plan is snapshotted into a session, and from then on the session records reality: actual reps, actual weight, actual rest, what you skipped, and timestamps for pacing.

Three tables, mirroring the plan

  • workout_session — the performed instance header (status, timers, the datetime from your sketch).
  • session_exercise — snapshot of each planned exercise, plus live status.
  • session_set — the heart of it: planned vs. actual for every individual set.
Why mirror the plan instead of just pointing at it? History integrity. Editing or deleting "Push Day A" tomorrow must not alter what you did today, so the session carries its own snapshot of every number. You always start from a saved plan (your decision — no ad-hoc workouts), so workout_id is required; the snapshot is what lets you then freely alter the workout during the session without corrupting the original plan.

Planned vs. actual is the analytics goldmine. Because every set stores both, you can ask: did you hit your targets? are you progressively overloading? how does actual rest compare to planned (are you rushing)? And it's exactly the diff Bob compares to make suggestions — though the sequence of changes lives in the event log (§10).
Unilateral volume (§3) — one row per set. A single-arm exercise still records one session_set row per set, and the live UI shows one set (never a separate "left" and "right"). The logged reps/weight describe what you did per side (you perform the same on each arm), and analytics multiply by 2 when laterality = unilateral to get true working volume. bilateral and alternating count their reps as-is.
If you ever need to log asymmetric sides (e.g. 10 reps left, 8 right after an injury), we add optional nullable actual_reps_right / actual_weight_lbs_right override columns later — the main columns stay the "both sides" value, so it's a non-breaking add and the UI stays single-set by default.

Lifecycle of a session

  1. Start Workout → insert workout_session (in_progress, workout_id required), then snapshot each plan exercise into session_exercise and expand its sets into session_set rows (all pending). Planned numbers prefer your last-performed values where available (§11) and fall back to the plan/catalog defaults.
  2. During → as you tap "+1", flip a set to completed and write the actuals + completed_at; the rest timer fills actual_rest_seconds. Any change (more weight, extra rest, added set) writes the actuals here and appends a session_event (§10).
  3. Finish → set status = completed, stamp ended_at and the timer totals. (Leaving early without finishing → abandoned.)

10 Session event log

A lightweight, append-only timeline of everything you change mid-workout. This is the raw material for Bob's between-rounds suggestions — without it, he can see the final numbers but not the story of how you got there.

Why a separate log when sets already store planned vs. actual? Planned-vs-actual is a single before/after. Your suggestion examples need sequence and repetition: "you added rest two sets in a row", "you bumped weight by 10, then 20 — want 30 and 40 next?". That's a series of timestamped events, which a set row can't express. The log captures the narrative; the set row captures the outcome.

Lightweight now, extensible later

"Lightweight" means: one table, a typed event_type, and a flexible payload jsonb for the specifics. We don't model a bespoke column set per event type yet. When patterns stabilize, we promote hot fields out of JSON into real columns — a non-breaking change.

How Bob uses it. Between rounds (during rest), the app queries the session's events since the workout started, looks for patterns (monotonic weight increases, repeated rest bumps), and proposes an action. If the user accepts, the app writes the new actuals to the upcoming session_set rows and logs the change as more events — the loop closes on itself.
It also doubles as an audit trail and undo source. Because it's an ordered, immutable record of intent, you can reconstruct exactly what the user did and when — useful for debugging, undo, and future ML on workout behavior.

11 Smart defaults & derived views

A small but high-impact idea (§5 of our discussion): the app should feel like it remembers you. Instead of always starting a session from the catalog's static defaults, seed planned numbers from what you actually lifted last time.

Why a view, not new columns? "Last performed" is fully derivable from data we already store in session_set. Computing it on the fly (a view) means there's nothing extra to write, nothing to keep in sync, and no risk of drift. It reads the log we already trust.

View: user_exercise_last_performed

The most recent completed set per (user, exercise) — the basis for smart seeding and quick "last time you did…" UI.

create view user_exercise_last_performed as
select distinct on (ws.user_id, se.exercise_slug)
       ws.user_id,
       se.exercise_slug,
       ss.actual_weight_lbs,
       ss.actual_reps,
       ss.actual_duration_seconds,
       ws.started_at as performed_at
from   session_set ss
join   session_exercise se on se.id = ss.session_exercise_id
join   workout_session  ws on ws.id = se.session_id
where  ss.status = 'completed'
order  by ws.user_id, se.exercise_slug, ws.started_at desc;

Seeding precedence at "Start Workout"

When expanding a plan into a session, each planned number is filled by the first available of:

  1. Last-performed value for that user + exercise (this view), if any — so progressive overload carries forward automatically.
  2. The plan's workout_set / workout_exercise snapshot.
  3. The catalog exercise default (the ultimate fallback for a brand-new exercise).
Composability. This view also powers analytics and is a natural input to Bob ("last time you hit 8×60 lb — try 8×65?"). If performance ever demands it, the view can be promoted to a materialized view or a maintained user_exercise_stats table with zero change to the tables above.

Cardinalities at a glance

  • A user has many plans, many sessions, and many score readings.
  • A plan has many workout_exercises; each may have many optional workout_sets.
  • A session has many session_exercises (each with many session_sets) and many session_events.
  • An exercise is referenced by plans, sessions, and score readings, but owns none of them — it's the shared vocabulary.
Snapshot boundaries (where the arrows intentionally "go cold"). workout_exercise → exercise and session_* → workout_* keep the reference for analytics, but the numbers are copied, not read live. That's the deliberate firewall that protects history.
